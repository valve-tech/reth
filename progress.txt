WHY THIS EXISTS
---------------
Firehose must trace pre-execution system calls (EIP-4788 beacon-root,
EIP-2935 block-hash history). Stock alloy-evm does NOT route system calls
through the Inspector: `EthEvm::transact_system_call` (crates/evm/src/eth/mod.rs)
calls `self.inner.system_call_with_caller(...)` unconditionally. So with stock
alloy-evm the firehose inspector never sees the system-call frame.

To fix this the valve fork patches alloy-evm via reth's `[patch.crates-io]` to a
fork that adds:

    fn transact_system_call(&mut self, caller, contract, data) {
        if self.inspect {
            self.inner.inspect_system_call_with_caller(caller, contract, data)
        } else {
            self.inner.system_call_with_caller(caller, contract, data)
        }
    }
    // + import revm::InspectSystemCallEvm

THE PRYSM-PARITY RULE (the discipline — get it wrong and the chain forks)
------------------------------------------------------------------------
prysm-pulse is the supermajority/canonical client. lighthouse MUST produce the
same VALUE, decided by reading prysm, NOT by the spec's arbitrary-precision ideal.
Two directions, per site:
  - prysm uses math/big (full precision)  -> lighthouse must WIDEN to u128
  - prysm uses wrapping uint64            -> lighthouse must WRAP (wrapping_*)
Widening a site prysm wraps, or wrapping a site prysm widens, is a silent split.

THE 4 FIXES (all on lighthouse-pulse master, signed/verified)
-------------------------------------------------------------

           (prysm uses big.Int). HALT class — this is what took the box down.
  e970792  reward burn (common/pulse.rs): safe wrapping_mul (prysm wraps uint64).
  718c7ad  slashing product (process_slashings): wrap sum_slashings*multiplier
           (prysm wraps uint64 at epoch_processing.go:201).
  5482ff4  PulseChain-magnitude regression harness (see below).
  56fbe85  slashings-vector accumulation (slash_validator): wrapping_add, not

FIX 1 — msgboard unbounded outbound channel = remote OOM — ✅ DONE 2026-08-02
==============================================================================
Full write-up: docs/msgboard-parity-gaps.md §15. Summary of what shipped:

  1. Bounded the per-connection outbound queue:
     mpsc::unbounded_channel -> mpsc::channel(MAX_QUEUED_OUTGOING_FRAMES = 8).
     Every frame is <= one 100 KiB packet, so ~800 KiB/peer, ~24 MiB across the
     30-peer inbound default.
  2. Made the sends await. handle_incoming / send_board_message_ids are now
     async. They share a task with the read loop, so a full queue stops us
     draining ProtocolConnection — that is what bounds the backlog rather than
     relocating it.
  3. Added OUTBOUND_SEND_TIMEOUT = 30 s, paid ONCE PER STALLED PEER via a
     stalled flag on OutboundQueue. NOT optional and NOT in the original plan:
     the mux's inbound to_satellite queue is itself unbounded upstream
     (multiplex.rs:289) and it keeps reading the socket regardless, so waiting
     forever would just move the unbounded growth upstream.
     TWO EARLIER SCOPINGS WERE WRONG, both caught by adversarial review:
       - per send   -> one request stalled the reader chunks x 30 s (meas. 60 s)
       - per frame  -> a flooding peer throttled the reader to ONE FRAME PER
                       30 s (meas. 300 s for 10 frames) while the unbounded
                       inbound queue filled at line rate. Same outcome as
                       waiting forever, i.e. the fix wasn't doing what §15.1
                       claimed. Fixed by the stalled flag.
     Both now have tests + negative controls.
  4. Chunked the outbound GetBoardMessages at MAX_IDS_PER_FRAME. This is a
     CORRECTNESS fix, not just a size bound: §14.3 capped our responder at 846
     distinct IDs, so an unchunked request over that lost the overflow silently
     against another reth node. §14.4's first open item, closed.
  5. New counter msgboard.outbound_dropped.

  DEPARTURES FROM THE ORIGINAL PLAN (both reasoned in §15):
   - The response BYTE ceiling was evaluated and REJECTED (§15.2). Response
     bytes are already bounded by MAX_IDS_PER_FRAME x size_limit, and size_limit
     is local operator config — nothing attacker-controlled is left to bound.
     A ceiling would only truncate honest first-connect responses, and truncated
     messages are never re-requested (reth asks only on announcement).
   - Reputation escalation on sustained overflow NOT done (§15.5). Backpressure
     can mean a congested link, not abuse. Revisit if outbound_dropped goes
     non-zero against otherwise-healthy peers.
   - The get_messages_for_ids lock-contention concern was OVERSTATED (§15.4):
     PoWMsg::data is alloy Bytes (refcounted), so the clone under the lock is
     ~96 B/message, not 8 KiB. ~81 KiB for a full request. No change made.

  Every new test was verified to fail with its fix reverted; the controls are
  tabulated in §15.1. 129/129 msgboard tests green.

  UPSTREAM (checked 2026-08-04, recorded in §15.6)
   - The unbounded inbound to_satellite queue was reported upstream TWICE and
     both were closed unmerged: PR #18702 (2025-09-25, bounds to_primary AND

   - reth's SECURITY.md: report vulns to security@tempo.xyz, NOT a public issue.
   - CORRECTION (§15.7): reth's custom-rlpx-subprotocol EXAMPLE does NOT have
