# reth v2.9 (evm2) port plan

Status, 2026-10-29: in progress on branch `upgrade/reth-2.9` (local). The owner approved starting the firehose port at once, not waiting for StreamingFast. The fleet stays on 2.8.x until this port passes its tests and evm2 has had production time (valve's decision).

## What v2.9 changed

reth v2.9.0 replaces revm with evm2 (paradigmxyz/reth#25002). evm2 is pinned by git commit (alloy-rs/evm2 `f93318f`). revm, revm-inspectors, alloy-evm and `reth-revm` are gone. The Ethereum block executor (`EthBlockExecutor`) now lives in `reth-evm-ethereum`.

## Done

- Merge of v2.9.0: all 23 conflicts resolved, in commit `eefa16e65c`. The upstream crates below the fork's crates compile.
- `crates/pulsechain/node/src/evm.rs` rewritten on evm2. It is not compiled yet, because it depends on `reth-firehose`.

## PulseChain EVM on evm2

- Chain ID per block: `EthEvmEnv::version.chain_id`.
- Ethereum post-Merge replay (`ETH_MAINNET_MERGE_BLOCK` up to the `PrimordialPulse` block): the spec is MERGE, then SHANGHAI from Ethereum's Shanghai timestamp. The block env needs no change: evm2 fills `prevrandao` from `mix_hash`, and the replayed headers already have difficulty 0.
- No proof-of-work reward in that range: the inner `EthBlockExecutor` gets Ethereum's `MAINNET` chain spec for those blocks. The reward is computed from the chain spec in `EthBlockExecutor::new`, and `PulseChain`'s spec still pays it there.
- Withdrawals in that range: upstream filters them by the block's EVM spec, and sums them per address. The fork's own withdrawal code is no longer needed.
- `PrimordialPulse`: committed as one `PendingState` through `EthBlockExecutor::commit_pending_state`, after the last transaction and before the inner executor finishes. In v2.8 it ran after the reward and withdrawals. Both only add to balances, so the order does not change the state, as long as the fork block's beneficiary and withdrawal addresses are not accounts the transition destroys or rewrites. A test must check this against the real fork blocks.
- A selfdestructed account is written as `original -> None`. `BlockState::commit_account` marks it `Destroyed`, and the bundle wipes its storage. `PendingState` cannot express "wiped, then recreated" for one address. The two deposit contracts have different addresses, and the writer panics if a later write hits a destroyed account.
- The new deposit contract is no longer marked "created" (v2.8 used `mark_created`). The result is the same if `0x3693…3693` had no code before the fork. A test must check this.

## Firehose on evm2

### Inspector

The evm2 `Inspector<T>` hooks are `initialize_interp`, `step`, `step_end`, `log`, `call`, `call_end`, `create`, `create_end` and `selfdestruct`. For the standard types, `T::Host` is the full `evm2::Evm`, so a hook reaches all of the state through `interp.host()`.

The hard part is the journal. In v2.8 the inspector scanned revm's fine-grained journal (BalanceChange, BalanceTransfer, NonceChange, NonceBump, CodeChange, AccountCreated, StorageChanged) at each call or create entry and exit, and emitted one tracer event per entry. evm2's journal has one `AccountChange` entry: a snapshot taken before the first change to an account.

Plan: keep the same scan points. At each scan point, for every account the evm2 journal names in this transaction, compare its current info (`State::account_info_untracked`) with a shadow copy of the last emitted values, and emit balance, nonce and code changes from the difference. Within one frame, an account's balance changes only through a sub-call (a scan point) or through SELFDESTRUCT (its own hook), so the diff should give the same events as v2.8. The firehose golden tests (`crates/firehose-tests`) decide whether it does.

### Ownership of the tracer

evm2 holds an inspector as an owned box (`Evm::set_inspector`, given back with `clear_inspector_as::<I>()`). Per call, it also accepts a borrowed one (`Evm::transact_with_inspector(tx, &mut dyn Inspector)`). v2.8's `LiveTracedEvm` type and its lifetimes are not needed.

### System calls

evm2 does not inspect system calls (`evm2/src/evm/system.rs`: "System calls are not inspected"). `PulseChain` is pre-Cancun and has none, but chain 1 and Sepolia do (EIP-4788, EIP-2935). That needs a valve fork of evm2 with an inspected system-call path, the same patch as the v2.8 alloy-evm fork. It goes through `[patch."https://github.com/alloy-rs/evm2"]`, which upstream's Cargo.toml prepares.
